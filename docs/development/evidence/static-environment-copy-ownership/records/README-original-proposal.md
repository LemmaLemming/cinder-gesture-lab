## Why the checks repeat

The existing closed [runtime guard profile](../../docs/development/RUNTIME_GUARD_PROFILING.md) observes 2,944 Protocol checks in eight ticks. Its nearest instrumented edges reconcile as follows: 256 placement queries plus 64 source steps make 320 coordinator validations; each coordinator validates eight Protocol sources, giving 2,560 checks. The 128 permission queries plus 64 source-step response queries total 192 responses, with two Protocol checks each, giving 384 more. Their sum is 2,944. These are historical measured counts, not a new Shared59 profile.

Current source retains these edges: `placement_accepted` invokes coordinator `_binding_error` (Repulsion157–158); `step_source` obtains `_response_for` then coordinator `_binding_error` (177–186); `allows_source_step` obtains `_response_for` (386). Coordinator `_binding_error` iterates every retained source Protocol (647–657), and `_response_for` dispatches the actual Protocol response accessor (1008–1015). Protocol `response_state` calls binding validation before and after the owned response getter (213–221). Each Protocol `_binding_error` acquires a new `Route.static_environment_state` (381), which acquires a new collision signature and floor plan (Route222–225).

**No repeated successful native check can be safely coalesced under the present contract.** A binding check is itself observable: it invokes actual source native-bindings (Protocol392), owned response (405), and Scheduler source-control (417) callbacks. The response, control and profile accessors introduce further owned callbacks between validations (213–237). Unit validation checks surround separate codec callbacks (266–278), and Repulsion's `_native_boundary_state` calls three virtual Protocol accessors before its final binding check (987–990). Neither a common frame nor the absence of a yield proves those callbacks leave the world unchanged. Removing a repetition would change getter counts, first failure opportunities or subclass behavior.

The old type-filter experiment was withdrawn after a slower comparison. The full-world codec fusion candidate has conflicting whole-window timings and stays unselected. The separate configuration-reference candidate already has source review/native preparation; this proposal does not reproduce it. Shared59 fresh discovery is the current baseline. ## One narrower reduction: return-owned fresh signature trees

`candidate.patch` changes only `Route.static_environment_state`'s successful return. Both current signature trees are constructed afresh, locally and without exposure during this call. Returning them directly can avoid their two recursive defensive-copy operations. It removes **no validation, signature acquisition, native getter, source/Scheduler callback, codec walk, guard, error branch or deadline**.

The collider list/rows/shape rows are freshly allocated at Route516,532,543–548. `_shape_data` constructs fresh dictionaries, encoded point arrays and scalar leaves (615–634), and `_transform` / `Codec.vector3` construct fresh arrays (637–638; Codec23–24). Floor signature rows are fresh dictionaries with freshly flattened scalar Rect2 arrays (401,433). Their actual collision handles are confined to the separate `regions` array; the returned floor signature excludes those handles. No source/native shape container is returned by reference. `Codec.value_error` checks but never publishes or retains these trees.

The sole possible foreign nested container origin is `signature.engine`, sampled from ProjectSettings at Route552. For **any Array or Dictionary engine value**, the proposal returns the literal original deep copies at the original post-floor-plan boundary. This preserves the existing accepted domain and detachment semantics even when this unusual configuration holds an aliased JSON tree. For all other admitted engine types, the engine is a JSON scalar with value semantics and every nested collider/floor container is freshly owned by the result. The branch reads only the already sampled value; it does not fetch settings again. Dictionary/Array inspection and copying add no owned callback.

The common scalar-engine branch returns fresh trees on every call. Mutating one returned tree cannot alter native state, another result, a future acquisition, or a retained Protocol descriptor; those references were never exposed before the return. Array order, field order, numeric bits/types, shapes, scalar contents, complete validation and exact error precedence stay unchanged. The foreign-container branch retains the full original return expression. There is no cache, membership assumption, private proof token or relaxed contract.

This is an allocation reduction, **not a reduction of the 2,944 validation checks**. Applied to the historical scalar-engine profile, it would avoid 2,944 world-tree plus 2,944 floor-tree deep-copy calls; that is a source-derived operation count, not a measured saving. Neither the old profiles nor this source reasoning establish the time spent in these copies, a speedup, sustained FPS or desktop performance completion.
